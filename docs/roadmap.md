## 2. 当前应用能力查询 `get_app_capabilities`

- 新增工具 `get_app_capabilities(app, window?)`：逐项回答辅助功能树、截图、OCR、坐标指针、键盘、浏览器扩展、前台（`run_in_front`）、文件面板、剪贴板此刻是否可用，不可用时给出原因，可用时给出限制（例如“Chromium 网页忽略后台指针事件”“锁屏时须 30 秒内的截图坐标”），并列出此刻能用的工具。只读：不启动应用，不发送任何输入，急停时也可查询；guardian 模式下不触发临时解锁。
- 每次调用都重新采集事实（锁态、direct/guardian 模式、权限、应用进程与隐藏状态、窗口列表、锁屏时可接收键盘的活动窗口数、截图坐标的时效、已连接的浏览器及其 pid、客户端能否询问用户）。结果带版本号；同一 MCP 会话里再次查询时说明与上次相比变了什么（session、windows、browsers、permissions 及各通道）。
- 判定逻辑是纯函数 `CapabilityReport.evaluate`，锁屏可用的工具集合与 direct 模式实际放行的集合共用 `DirectLockedUse.lockedTools`，不会各说各话。
- 顺带修复：浏览器桥接宿主在 `bind` 与 `listen` 之间被客户端连接时，客户端会把它的 socket 当作陈旧文件删除，宿主从此不可见（浏览器重启时频繁查询必现）。现在宿主在临时路径监听后原子改名；客户端只在对应浏览器进程已退出时才删除 socket。
- 模拟测试：`Tests/SkfiyKitTests/CapabilitiesTests.swift` 11 项，覆盖解锁/锁屏/无 direct/已结束/未知锁态、权限缺失、隐藏/最小化/无辅助功能窗口、终端与宿主保护、浏览器连接变化、急停、客户端不能询问、JSON 与文本一致、陈旧 socket 判定。
- 专用测试窗口：`scripts/test_capabilities.py` + `scripts/fixtures/ScenarioFixture.swift`（控制文件驱动的测试应用，锁屏时也能开关窗口、改文字、动画、隐藏、移动，并独立记录收到的点击和按键）。2026-10-05 00:45 锁屏实测 24/24 + 1/1 通过：单窗口时键盘可用；开第二个窗口后版本变化、指出 windows/keyboard 变化、键盘因两个活动窗口不可用；关窗后恢复；`get_app_state` 后报告截图坐标时效；急停开关；未用 direct 模式启动的会话说明原因；查询前后测试应用收到的输入为零。锁态采样全部为锁定。
- 真实应用：Finder（锁屏时键盘可用与否与其活动窗口数一致）、终端（无键盘/指针）、未运行的 Calculator（说明锁屏时不启动应用）、Chrome for Testing（扩展连接时浏览器通道可用；退出后不可用；重启重连后恢复）。
- 限制：解锁状态下的隐藏/显示和 Finder 检查已写好，待用户解锁后运行；权限撤销只在模拟测试中覆盖（测试不改系统权限）；锁态切换本身由用户触发，测试只在两种状态下分别核对。

## 3. 锁屏等待 `wait_for`（direct 模式）

- direct 模式接入 `wait_for`：等文字出现（`text`）、消失（`gone`），或不给文字时等窗口画面稳定（`stable_for`，默认 1 s）；`region`（最新截图的像素矩形）只看窗口的一部分，忽略别处的时钟或转圈；`timeout` 0.5–60 s。满足后返回新截图与文字坐标；超时返回错误并附当前状态。
- 不发送任何输入。每次观察前后检查：锁态（解锁、锁态未知、解锁后又锁上）、急停、`locked_use_end`、应用进程身份、权限、窗口是否还在、有 `region` 时窗口是否移动或缩放；任一变化立即停下并说明原因，同时作废旧截图坐标。
- 判断画面稳定用受控截图差分：把截图缩成 160 像素宽的灰度指纹，变化像素少于 0.2% 视为未变（闪烁的光标不算变化）。等文字时只在画面变化后才重新 OCR。
- 顺带改进锁屏 OCR：direct 模式现在按显示器的原始分辨率（Retina 为 2 倍）截一次图，在其上识别文字，再缩成常规截图给模型，坐标仍对应模型看到的截图。基线中 1 倍截图把 “6a9344d055” 识别成 “бa9344d055”、把一行拆成几段的问题因此缓解。
- 取消：MCP 服务器现在处理 `notifications/cancelled`——请求按顺序执行，所以取消通知不排队，直接取消正在运行的工具；被取消的请求按 MCP 规定不再回复。解锁状态的 `wait_for` 也改用同一等待引擎，同样可取消、同样说明停下的原因。
- 模拟测试：`WaitingTests` 8 项（延迟文字、消失与 OCR 拆词、动画后稳定且忽略光标、超时、锁态变化停下、窗口关闭停下、取消、像素指纹与区域）；`MCPCancellationTests`（取消后无回复、执行体收到取消）。
- 专用测试窗口：`scripts/test_wait.py`，2026-10-05 00:56 锁屏实测 16/16：3 s 后出现的文字在 3.3 s 识别到；2 s 后消失在 2.7 s 判定；3 s 动画结束后才判稳（动画仍在时不提前返回）；`region` 只看文字区时 1.8 s 返回而动画仍在进行；2 s 超时报错并附截图；取消后下一次调用 0.3 s 即得到回答且被取消的请求没有回复；被等待的窗口关闭时 2.3 s 停下并说明“窗口已关闭”；全程测试应用收到的按键和点击为零。锁态采样 113/113 为锁定。
- 真实应用：Chrome for Testing 前台标签页的测试页，经扩展点“Load later”后，锁屏 `wait_for` 用 OCR 在 3.2 s 识别到 “LOADED …”（页面自己回报此时加载完成），随后判定页面画面稳定。6/6，锁态采样全部为锁定。
- 发现并修正的测试问题：测试应用的动画周期（0.5 s）恰好等于一次采样循环时画面看起来不动——改为单程扫动；真实世界中严格周期性的动画同样可能被误判为稳定，此时应改用 `text` 或 `region`。
- 限制：锁态切换中途停止只在模拟测试中验证（测试不改变系统锁态）；解锁状态的 `wait_for` 现在经同一引擎运行，解锁实测待用户解锁后补跑 `scripts/test_wait.py`。

## 4. 锁屏局部放大 `zoom`（direct 模式）

- direct 模式接入 `zoom(app, x, y, width, height, scale?, ocr?)`：区域以最新截图的像素给出；按窗口所在显示器的原始分辨率重新截取该窗口（不用旧图），切出区域并放大到 `scale` 倍（默认为显示器的全部细节，Retina 上为 2；1–8 倍，超过显示器细节时注明“放大但无新细节”；始终在模型的图片尺寸限制内，模型不会再缩放它）。默认附上放大图里识别出的文字，每段同时给出放大图坐标和对应的截图坐标。
- 坐标映射：返回 `截图 x = 起点 + zoom_x / 倍数` 的公式和 `zoom_id`；`click`、`scroll`、`drag` 可传 `zoom_id` 加放大图上的 x/y，由 skfiy 换算。切图按显示器整像素进行，实际显示的区域可能比请求宽出不到 1 个像素，映射用的是实际显示的区域，所以是精确的。
- 拒绝沿用旧坐标：截图超过 30 秒、窗口移动或尺寸变化（放大时重新取窗口位置比对）、锁态变化或进程变化时，`zoom` 拒绝并作废该截图；`zoom_id` 只对产生它的那张截图有效，新的 `get_app_state` 或任何操作后的新截图都会使它失效。
- 解锁状态的 `zoom` 同样给出公式和 `zoom_id`，窗口在截图后移动或缩放时拒绝；`scale`、`ocr` 两种状态一致。
- 模拟测试：`ZoomTests`（1、2、2.5、3、4 倍下放大图坐标与截图坐标、屏幕坐标互逆；倍率受模型图片上限约束；公式文本；小数边缘的区域切图后用红点验证映射误差 < 0.6 pt；Retina 与负坐标显示器的几何）。
- 专用测试窗口：`scripts/test_zoom.py`，2026-10-05 01:04 锁屏实测 27/27：6 pt 小字放大后 skfiy 的识别和独立 OCR 都准确读出（之后共 5 次运行中 6 pt 有 1 次错 1 个字符，测试应用随后改为同时画 6 pt 与 7 pt，7 pt 3/3 准确，作为必过项）；1/2/3/4 倍下，独立程序在放大图中找到 10×10 pt 红色目标，按 `zoom_id` 点击，测试应用记录的点击点与目标中心相差均 < 0.2 pt，公式换算误差 ≤ 0.4 px；窗口移动、缩放后 `zoom` 被拒、旧 `zoom_id` 被拒；新截图后旧 `zoom_id` 被拒；31 秒后被拒；所有被拒的调用都没有给应用发送任何输入。锁态采样全部为锁定。
- 真实应用：Chrome for Testing 中的测试页（锁屏）。先放大一大块定位，再对小字所在行 4 倍放大：9 px 的随机十六进制串 2/2 次被准确读出（整窗 OCR 1/2 次），8 px 1/2 次，7 px 0/2 次（差 1 个字符）——7 px 在 Retina 上约 14 个设备像素，已到显示器精度的边界，放大不增加细节。放大图中文字换算回截图的位置与整窗 OCR 的位置相差 ≤ 4 px。
- 限制：Chromium 窗口在锁屏时不接受指针事件（见兼容表），所以真实应用只验证了读取与坐标换算，按放大图坐标点击在测试应用中验证；解锁状态的 `zoom` 实测待用户解锁后补跑。

## 6. 操作结果验证 `expect`

- `click`、`type_text`、`press_key`、`set_value`、`scroll`、`drag`、`perform_secondary_action`、`select_text` 新增可选参数 `expect`：`text`（出现）、`text_gone`（消失）、`value_changes` / `value`（元素或焦点字段的值，需辅助功能，锁屏时直接拒绝且不发送）、`window_closed`、`window_opened`、`changed`，可设 `timeout`（默认 5 s）。
- 动作前先观察一次，动作后持续观察直到满足、目标变化或超时，结果首行给出四种结论之一：`verified`（已验证完成）、`no_effect`（未观察到效果：窗口毫无变化）、`target_changed`（目标变化：所操作的窗口关闭、出现了别的窗口、应用退出、锁态改变）、`timeout`（有变化但不是预期的）。未验证时结果标为错误，并附上此刻的状态（截图与树或识别文字），而不是动作刚发出时的截图。
- 观察在两种状态下各用各的来源：解锁时读辅助功能树的文字、窗口列表、元素值；锁屏时用窗口截图的像素指纹和识别文字、窗口列表。像素变化的判断改为 640 像素宽的灰度指纹，任何几个像素以上的变化都算，只有细长竖条（闪烁的光标）不算——原先按变化比例判断时，小字号状态栏从 “ready” 变为 “apply 1” 只占 0.15%，会被当作没有变化（`wait_for` 的稳定判断与是否重新 OCR 同样受益）。
- 不盲目重试：skfiy 不会自动重试任何操作。标签像“提交/发送/支付/删除/确认”（中英文）的按钮、Return 键，或显式 `idempotent: false` 的操作视为只能发生一次；它的效果未被验证（没有 `expect`，或结论不是 verified）时，紧接着原样重复会被拒绝且不发送，提示先用 `get_app_state`/`wait_for` 查看；看过之后或传 `confirm_repeat: true` 才放行。已验证的提交不阻止有意的下一次。锁屏时按钮标签取点击点处识别出的文字。
- 顺带修复：锁屏时点击使所操作的窗口关闭（如对话框的“完成”）后，原先会因截不到该窗口而报错，掩盖了已经发生的操作；现在说明窗口已关闭并显示应用剩下的窗口。
- 模拟测试：`VerificationTests` 8 项（解析、四种结论、窗口与值、像素变化、风险标签与按键、重复保护）、`WaitingTests` 新增“小字变化算变化、光标不算”。
- 专用测试窗口：`scripts/test_verify.py`，2026-10-05 01:14 锁屏实测 13/13：点 Apply 0.5 s 验证；点 Noop 判为 no_effect（测试应用确实收到了这次点击，只是没有可见效果）且附当前状态；期待落空但界面有别的变化判为 timeout；打开对话框 window_opened 验证；在对话框里点“完成”却期待文字时判为 target_changed（窗口已关闭）；window_closed 验证；锁屏时值期望被拒且未发送；Submit 期待落空后原样重复被拒（测试应用的提交次数仍为 1），查看状态后再次提交被放行并验证（提交次数 2），已验证的提交不阻止下一次（提交次数 3）。锁态采样全部为锁定。调试中测试脚本按 OCR 找“Apply”时误中状态栏里的 “apply 1”，skfiy 如实判为 no_effect——正是这一功能要防的“无效点击”。
- 真实应用：TextEdit（锁屏），输入后文字出现 0.6 s 验证；按一个无作用的键（F15）判为 no_effect；滚动判为有变化。4/4，锁态采样全部为锁定。
- 限制：值类期望在锁屏时不可用；风险操作按标签识别，没有文字标签的图标按钮需显式 `idempotent: false`；解锁状态实测待用户解锁后补跑。

## 9. 多窗口与多显示器定位

- 窗口身份贯穿读取与操作：`get_app_state` 的窗口行与“其他窗口”列表都带窗口 id（解锁与锁屏一致）；`window` 参数可传 id；多个窗口匹配同一标题时拒绝并列出各自 id，不猜。点击、输入、按键、滚动、拖拽可带 `window_id`：最新截图不是该窗口时拒绝且不发送。
- 坐标不偏移：解锁状态下按 x/y（或 `zoom_id`）操作前，核对截图所示窗口仍在、位置与尺寸未变；窗口移动、缩放、跨屏移动或关闭后拒绝旧坐标（此前解锁状态不检查，窗口挪动后点击会落到别处）。按元素编号的操作不受影响。锁屏状态原本就逐次核对，现在拒绝时说明具体原因：窗口移动/缩放、截图过期，或窗口已关闭——若出现同标题的新窗口，指出它是被重建的、新 id 是多少。
- 多显示器与 Retina：显示器几何改为纯函数（`DisplayInfo`、`display(for:among:)`、`backingScale(for:displays:)`），全局坐标采用左上角原点，主屏左侧/上方的显示器为负坐标；窗口所在显示器按中心点判定，跨屏时取包含中心者，完全离屏时取最近者；截图、OCR 与 `zoom` 都按窗口所在显示器自己的缩放比例。
- 锁屏多窗口键盘输入可行性实验：见 [locked-use/README.md](../locked-use/README.md)。结论是无法事先确认接收窗口，继续拒绝；实验脚本保留，可在其他机器或系统版本上复测。
- 顺带修复 OCR：在一个 TextEdit 窗口上，Vision 对 2 倍分辨率截图只识别出标题，1 倍时却能读出全部 77 行等宽文字。现在两种分辨率各识别一次并合并（以高分辨率结果为主，补上它漏掉的行），解锁与锁屏路径都用。
- 模拟测试：`DisplayGeometryTests`（主屏 Retina、左侧 1× 负 x、上方 Retina 负 y：窗口归属与缩放、跨屏与离屏、截图与放大坐标在负坐标上的换算、大窗口降采样后的换算）、`TextRecognitionTests` 新增合并用例。
- 专用测试窗口：`scripts/test_windows.py`，2026-10-05 01:26 锁屏实测 8/8：两个同标题窗口按标题选择被拒并列出两个 id；按 id 选中副本；`window_id` 与截图不符被拒且未发送；点击副本的“完成”只关闭副本，主窗口计数不变（不串窗）；窗口关闭后重建（同标题新 id）时旧截图被拒并指出新 id；主窗口移动后旧坐标被拒，重新截图后在新位置命中同一按钮。锁态采样全部为锁定。OCR 合并改动后，等待、放大、验证、能力、窗口五套锁屏测试全部重跑通过。
- 真实应用：TextEdit 同时打开两个同名 `twin.txt`（不同文件夹，内容 Alpha / Beta），锁屏时按标题选择被拒并列出两个 id；按 id 分别截图；在 Beta 窗口按坐标滚动后其首行从 5 变为 77，Alpha 窗口首行仍为 1。4/4，锁态采样全部为锁定。
- 限制：本机只有一块内置显示器，多显示器、跨屏移动和外接 1× 显示器只在模拟测试中验证，未做实机验证；创建虚拟显示器会改变用户的窗口布局，因此没有做。解锁状态的窗口测试待用户解锁后补跑。
